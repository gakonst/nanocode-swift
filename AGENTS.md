# Development

This repository is nanocode-swift (gakonst/nanocode-swift): the nanocode Rust SDK compiled into a static library for Apple platforms, the Swift package that drives it, native AppKit and UIKit views, and example apps for macOS and iOS, so an app writes only Swift and builds no Rust beyond `scripts/build-ffi.sh`. It follows gakonst/nanocode-ts: that package compiles the SDK into one WebAssembly module and a TypeScript host supplies SQL, HTTP, sockets and tools; here the SDK runs natively inside the app, so it keeps its own HTTPS and WebSocket transports (reqwest and tokio-tungstenite with the platform verifier), its own SQLite file, its own QuickJS Code Mode engine, its own shell tools on macOS and, on iOS, nanocode-ts's simulated bash in a QuickJS runtime of its own, and Swift supplies only configuration, host tools, credentials and the UI. Its sibling `../nanocodex` supplies the SDK; `sdk-revision.json` records the SDK master revision this package builds against, and `ts-revision.json` the nanocode-ts revision whose simulated bash and Code Mode cell prelude `src/shell/` bundles. Generic agent, durability, turn, event, hand and payment logic belongs in the SDK or in mpp-rs, host-agnostic bridge glue in `src/*.rs` and `Sources/Nanocode`, views in `Sources/NanocodeKit`, and an application's business logic (its tools, prompts, skins) in the app.

## Rules

These rules come from gakonst/nanocode's `AGENTS.md` and apply to every change here.

- Do not add code comments, doc comments, or comment headers. Names, types, and this file carry what a reader needs. Only comments that a tool reads stay, such as `// swift-tools-version` in `Package.swift`.
- Do not add tests, test targets, Cargo features, or test-only dependencies. Validate a change by building the XCFramework, `swift build`, the example apps with `xcodebuild`, and runs of `Examples/Console`, and record the commands and results here.
- `README.md` is the repository's homepage: the overview, products, quickstart and the demo recordings in `assets/` (GIFs of the demo app made with the `-NanocodeType`, `-NanocodeWindow` and `-NanocodeAppearance` launch arguments, optimized with `gifsicle -O3 --lossy=60`). Development guidance belongs in this file.
- Keep logs, traces, raw recordings, and scratch files in ignored `output/`. Never commit credentials or personal test data.
- Record what a change establishes in this file: the behavior, the reason the code cannot show, and the commands, inputs, dates, and before and after measurements. Correct or remove the entries that the change makes stale, so this file stays a description of the current code.
- The Rust side keeps state lock-free with `nanocode-sync` (`Atom`, `Slot`) as the SDK requires. Swift guards its small shared tables with `OSAllocatedUnfairLock`.
- Prefer simple code and small changes. Preserve unrelated work.
- Take every limit from a real platform or protocol constraint, a measured requirement, or explicit caller policy, and record its source here. Surface invalid states instead of hiding them with silent truncation, clamping, or fallback values.
- Benchmark performance changes with reproducible commands and inputs, and report before and after results. Keep cold builds, incremental builds, and runtime performance separate.
- Keep the development loop fast: build only what changed, reuse caches, and skip redundant checks. Honor requests to skip builds or CI.
- Work in the main checkout on `main` and push each completed change to `main`. Do not create worktrees or feature branches. Commit only your own changes, leave other dirty or untracked files alone, and rebase onto `origin/main` when a push is rejected.

## Layout

- `src/` is the crate `nanocode-swift` (`staticlib`): `bridge.rs` is the C ABI and its multi-threaded tokio runtime, `command.rs` the command table, `session.rs` the SDK's `TurnInbox` per open session over `nanocode_store_sqlite::SqliteSql` (one `nanocode.sqlite` in the app's data directory holds every session's `SqlStore` state and `SessionLog`), `config.rs` the session configuration and model clients, `tools.rs` Swift host tools as the SDK's `FunctionTool`, `files.rs` a native `FileHost` for file tools, `shell.rs` the simulated bash (see Simulated shell), `hand.rs` hands, `payments.rs` and `wallet.rs` machine payments, and `catalog.rs` the model catalog.
- `include/` holds `nanocode.h` and the `NanocodeFFI` module map; `scripts/build-ffi.sh` builds the crate for `aarch64-apple-darwin` (and `x86_64-apple-darwin` with `UNIVERSAL=1`), `aarch64-apple-ios` and `aarch64-apple-ios-sim` (and `x86_64-apple-ios`) and writes `build/NanocodeFFI.xcframework`. It runs one `cargo build` for every target and copies into the XCFramework only the files whose contents changed (`rsync -c`), so a Rust change leaves its headers alone and Xcode relinks the apps without recompiling their Swift (10.6 s for the Mac demo, against 117 s when the XCFramework was written anew). `PROFILE` is `fast` by default: release dependencies, and this crate at `opt-level` 1 with 256 codegen units and incremental compilation (`--config profile.release.package.nanocode-swift.*`, so the dependencies keep their release builds); `PROFILE=release` builds this crate at `opt-level` 3 too, as `scripts/publish-ffi.sh` does, and `PROFILE=debug` builds unoptimized libraries (370 MB for macOS arm64 on 2026-10-27). `PLATFORMS="macos"` limits the platforms. The crate is a `staticlib` only: an `rlib` beside it spent about 10 s per build writing metadata nothing reads. Measured on 2026-10-29 for one edit to `src/shell.rs` (Apple silicon, under heavy load from other builds): a release build of the crate took 34 to 65 s, 41 s of it in LLVM's passes, 21 s in code generation and 10.5 s in metadata (`-Z time-passes`), and `PLATFORMS=macos scripts/build-ffi.sh` with `fast` took 36 s including that build. SwiftPM recompiles `Nanocode` and every module above it whenever the library changes (it lists the copied `libnanocode_swift.a` as an input of each Swift compile; 21 to 23 s for `Console`), while Xcode only relinks; a Swift edit in `NanocodeKit` took 12 s to rebuild the Mac demo in Debug and 18 s in Release.
- `NanocodeKit` is the UI, in AppKit on macOS and UIKit on iOS from one source (`KitView`, `KitColor` and `KitFont` alias the platform types; no SwiftUI): `CloneViewController` and `CloneNode` are nanocode-ts's ChatGPT and Claude clone apps (`src/react/clones/ChatGpt.tsx`, `Claude.tsx` and their CSS, as nanocode-vercel-durable's `/chatgpt` and `/claude` render them) with `Skin.chatgpt` and `Skin.claude` carrying their CSS variables in light and dark: the sidebar of chats with hover rows and delete, the header (ChatGPT's model menu, Claude's centered title), the hero with the greeting, composer, prompt pills and footer, the transcript (user bubble, grouped tool calls as ChatGPT's "Ran code" card or Claude's collapsed cells, thinking blocks, markdown with code bars and ruled tables, the pulse or spinning spark), the composer with attachments, steer and stop, and the model list, which opens below the ChatGPT header and above the Claude composer. `CloneProps` carries what the host supplies (conversations and callbacks, `ClonePicker`, prompts, footer markdown, header actions such as a `ClonePill`, `titlebarInset` for a full-size-content window). Below 768 points wide the layout follows the clones' mobile CSS: the sidebar becomes a drawer over a scrim, the header shows its open and new-chat buttons, the user bubble widens to 85% and the hero shrinks; on iOS it keeps to the safe area and above the keyboard. `NanocodeChatViewController` is the conversation alone for an app's own window. Views are `Node` subclasses that measure and place their children themselves (`Stack`, `Flow`, `Label`, `TextNode` on `NSTextView`/`UITextView` for selectable text, `ScrollNode`, `InputNode`), and `Observer` re-renders on `Chat`'s Observation changes. Check layouts at phone width with the demo's `-NanocodeWindow 390x844` (`-NanocodeBackground YES` keeps it from taking focus, `-NanocodeNew YES` opens a new chat, `-NanocodeStyle chatgpt|claude`, `-NanocodeAppearance light|dark`, and `-NanocodeType YES` types `-NanocodePrompt` into the composer before sending it, for recordings).
- `Package.swift` exports four products. `NanocodeCore` is plain Swift with no Rust: `JSON`, `LoggedEvent`, `LiveEvent` (nanocode-ts's `liveEvent`, plus `user` events from `input.accepted`), `Transcript` (nanocode-ts's `Transcript`: paced reveal, paragraphs, one `ToolCell` per call with nested Code Mode calls, yielded cells and their `wait`s), `ToolInput`, `Turn.group`, `Activity`, the markdown block parser with `MarkdownStream`, `Highlight`'s tokenizer and `DataURL`. `NanocodeViews` is SwiftUI over it, also without Rust, kept for SwiftUI hosts such as tempoxyz/pyramid's app; this package's own UI and apps are AppKit and UIKit (`NanocodeKit`): `MarkdownView` with `MarkdownStream` and `Highlight` (ported from tempoxyz/pyramid's transcript), `CodeBlock`, `ToolCellView`, `ThinkingView`, `TranscriptView` over a `TranscriptState`, and `NanocodeTheme`. `Nanocode` is the runtime over the Rust library (`NanocodeRuntime`, `Session`, `Chat`, `Wallet`, `WalletMonitor`, `HandMonitor`, hands, runners, the model catalog). A host that renders nanocode events it receives some other way, such as from a server, uses only `NanocodeCore` and `NanocodeViews` and links no Rust. `NanocodeFFI` is the local XCFramework when `build/NanocodeFFI.xcframework` exists, else the release that `ffi-release.json` names (`url`, `checksum`, `fingerprint`), so apps such as tempoxyz/pyramid depend on the package without building Rust; the repository is private, so SwiftPM needs GitHub credentials (a `~/.netrc` entry for `github.com`) to download it.
- `Examples/Console` is a terminal client of `Nanocode` (`Console remote cloudflare|vercel [prompts…]` chats with a deployment through `RemoteSession` and reopens the conversation from its journal, and `Console remote-resume [id]` follows a turn a killed process left open, and `Console bash <script>` runs a script in the simulated shell): a prompt (`NANOCODE_PROVIDER`, `NANOCODE_MODEL`, an API key from `ANTHROPIC_API_KEY` or `OPENAI_API_KEY`, else the Tempo CLI wallet, `NANOCODE_RELAY_TOKEN` to take a machine through the relay, and `NANOCODE_WORKSPACE_TOOLS` (`all`, `simulated`, `files` or `none`) to give the session a workspace in the console's data directory with those tools, and `Console hand|runner` the same selection), or `Console hand|runner <url> <token> [name]` to make the process a hand or attachment runner. `Examples/Demo` is the nanocode.xyz demo as an AppKit app for macOS and a UIKit app for iOS, in the ChatGPT or Claude style (View menu, ⌘1 and ⌘2, or Settings). Settings is a page inside the main window, not a separate window or sheet (`SettingsNode` in `Shared/Settings.swift`): the account row at the bottom of the sidebar (`CloneProps.sidebar`: the Tempo Wallet, plan or API keys with what it has spent) or ⌘, opens it over the conversation, drawn in the clone's skin as grouped tables of rows with checkmarks, native switches (`NSSwitch`, `UISwitch` tinted with the Claude accent) and inline fields, for the account (how turns are paid, the wallet with its device code, spend per service, Add MACH and Disconnect, plan sign-ins, API keys, paid tools), where the agent runs, the style, the workspace folder, the relay command and this device as a hand, with safe-area padding on iOS; `-NanocodeSettings YES` opens it at launch. The agent runs on this device, Cloudflare or Vercel (`-NanocodeRunner device|cloudflare|vercel`, ⌥⌘1 to ⌥⌘3) (`project.yml` for XcodeGen; run `xcodegen generate` there, the project is not committed): conversations from the store, a model menu, a Tempo Wallet card, device tools (`device_info`, `open_url`, `clipboard`, `speak`, and in `Shared/DeviceTools.swift` the ones behind a system permission: `photos` (list, view, save as JPEG into the workspace, read text with Vision, add to the library), `contacts` (search, list, create, export as vCard), `calendar` and `reminders` (EventKit full access), `location` (Core Location and Apple Maps search), `notify` (local notifications, and on iOS one when a turn finishes in the background), `listen` (microphone and on-device speech recognition when the device has it), `bluetooth` (a BLE scan), `compose` (a prefilled message or email the user sends), `shortcut` (runs a Shortcut through the Shortcuts app), and on iOS `camera` (a photo, or a document scan with its text), `motion` (steps and activity) and `music` (the library and the system player); each writes what it saves under the workspace, where the shell reaches it), a workspace folder the user can choose (Settings ▸ Workspace: an `NSOpenPanel` sheet on macOS, the Files app's folder picker on iOS, kept as a bookmark and opened with security-scoped access, so sessions, the shell and the hand work on the folder's real files), a computer connected through the relay, and this device as a hand. The demo sends no instructions of its own, as nanocode-ts's hosts send none: models get upstream nanocode's prompts and tool text, the session environment and the host tools' descriptions. Launch arguments script it for checks: `-NanocodeWallet cli`, `-NanocodeProvider`, `-NanocodeModel`, `-NanocodePrompt`, and `-NanocodeShell '<script>'`, which runs a script in the simulated shell in the workspace and prints its output and exit status to stdout (`simctl launch --console-pty` shows it from a simulator). The iOS app asks for background time (`beginBackgroundTask`) while a turn runs and calls `resume()` when it returns to the foreground; it has not been run on a device or simulator.

## Bridge

`nanocode_start(config, length, callback, context)` starts a runtime for a data directory (`{"data_dir", "tempo_home"?}`), `nanocode_send(handle, bytes, length)` sends one command and `nanocode_stop(handle)` closes every session and hand and shuts the runtime down; it blocks, so Swift calls it from `deinit` off the main actor. Every message either way is one JSON object. Swift sends `{"id", "command": {"<name>": {fields}}}` (externally tagged, as nanocode-ts's commands) and gets `{"reply": id, "ok"}` or `{"reply": id, "error"}`; a command without `id` gets no reply. Rust sends `{"event": {"session", ...}}` (`logged` and `live` batches of the SDK's `LoggedEvent`s, `driving`, `turn` with the finished turn's report, `waiting`, `resumed`, `error`), `{"call": {"id", "kind": "tool", "body": {name, input, context}}}`, which Swift answers with the `reply` command, `{"hand": {"id", "event" | "stopped"}}` and `{"runner": ...}` alike, `{"wallet": {"prompt"}}`, `{"payments": {"status" | "notice"}}` and `{"log"}`. The callback runs on the runtime's threads; `Router` in `Runtime.swift` resolves replies and yields events into `AsyncStream`s synchronously, so a session's events stay in log order.

Commands: `models`, `sessions` (stored root sessions, newest first), `open` (a `Configuration`, see `config.rs`, which denies unknown fields), `close`, `submit`, `steer`, `move_queued`, `replace`, `cancel`, `turn`, `pending`, `page`, `settings`, `compact`, `checkpoint`, `permission_mode`, `settle`, `interrupt_subagent`, `close_subagent`, `reply`, `mcp_sign_in`, `mcp_sign_in_wait`, `plan_sign_in`, `plan_sign_in_complete`, `plan_status`, `plan_sign_out`, `hand_start`, `hand_stop`, `hand_status`, `runner_start`, `runner_stop`, `runner_status`, `shell_run`, `wallet_connect`, `wallet_use`, `wallet_cli`, `wallet_forget`, `payments` and `funding_url`. `open` builds one `Nanocode` runtime per session (`without_runners`, the session's workspace or `<data_dir>/workspace`) and opens its `TurnInbox`; a driver task per session calls `TurnInbox::drive` whenever a submit wakes it, retries `Waiting` and `Interrupted` turns with a backoff from 0.5 s to 30 s, and reports each finished turn. An `open` with `fork` (`session`, an open session's id) starts a new session from that one's conversation through `Runtime::switch`, which forks it when the configuration keeps the model and otherwise carries its transcript to the configuration's model or provider; with `checkpoint` (from the `checkpoint` command, taken before a turn) and `before` (that turn's request id) it forks the conversation as it was before that turn. The new session gets its own ID, which the reply carries, a copy of the parent's log up to the fork point, and a place in `sessions`.

## Sessions and tools

A session's provider is `claude` or `codex` with any model its harness serves (Haiku 5.5 and Luna by default). `auth` is `"tempo"` (machine payments, the default), `{"api_key"}`, `{"headers"}` or `"plan"`; `endpoint` replaces the provider's base URL. `"plan"` uses a Claude or ChatGPT plan through the SDK's `ClaudeSubscription` and `ChatGptSubscription` (`plans.rs`): `plan_sign_in` (`provider`, and `redirect_uri` for Claude) returns Claude's `authorization_url` or ChatGPT's device `verification_url` and `user_code`, `plan_sign_in_complete` (`code`, the redirect URL or the code Claude shows) finishes a Claude sign-in, ChatGPT's finishes on its own while `plan_status` polls, and `plan_sign_out` forgets it. Their state reaches Swift as `subscription_store` calls (`load` a `key`, `claude` or `chatgpt`, and `compare_and_swap` its `revision` and `payload`), which the app answers with a `SubscriptionStore` set through `NanocodeRuntime.setSubscriptionStore`. `KeychainSubscriptionStore(service:)` is such a store in the Keychain (one item per key holding `{revision, payload}`, compare-and-swap under a lock), and `PlanMonitor` drives the sign-ins for a UI: `status` per provider, `signIn(_:)` returning the step (ChatGPT's device code, which it then polls until approved; Claude's claude.com page with Anthropic's manual code callback, finished by `complete(_:code:)` with the code that page shows), `cancel` and `signOut`. The demo offers "ChatGPT or Claude plan" beside Tempo Wallet and API keys for turns on this device, and `Console plan chatgpt|claude [status|signout|<code>]` runs the same flows; on 2026-10-28 both sign-ins started (a claude.com authorization URL, and a device code for auth.openai.com/codex/device), and neither was completed against a real account. Codex plan sessions get no host web search. On 2026-10-28 both sign-ins started against the real providers with an in-memory store and signed out; none was finished. Workspace tools follow nanocode-ts's `workspace_tools`: `all` gives the SDK's native workspace tools on macOS (Claude's `Bash`, `Read`, `Edit`, `Write`, `Glob` and `Grep` from `nanocode::claude::runner_tools`, Codex's shell and `apply_patch`), and on iOS, where apps may not spawn processes, it means `simulated`: the host tools nanocode-ts gives its WebAssembly sessions, Claude's `Bash`, `Read`, `Edit`, `Write`, `TaskOutput` and `TaskStop` (`nanocode::claude::host_tools`) or Codex's `exec_command`, `write_stdin`, `apply_patch`, `view_image` and `update_plan` (`nanocode::codex_tools::host_tools`), over `NativeFiles` and the simulated shell. `simulated` selects them on macOS too, `files` keeps only the file tools (Claude's `Read`, `Edit` and `Write` or Codex's `apply_patch` and `view_image`) and `none` gives no workspace tools. Code Mode cells run in the SDK's native QuickJS engine on both platforms and call these tools as `tools.Bash`, `tools.exec_command` and the rest. Host tools (`HostTool` in Swift: name, description, JSON Schema parameters, `content` for text-and-image results) become `FunctionTool`s offered directly and inside Code Mode; `ToolResult.content` answers with `input_text` and `input_image` items. Claude sessions get the SDK's `WebSearch` (a nested Messages request through the same client, so it is paid the same way) and Codex sessions the SDK's host `web__run` (a nested Responses request with OpenAI's `web_search` tool) over `payments::Transport`, a `HostTransport` that sends it through the session's layer (machine payments, the API key or the configured headers), unless `web_search` is false. On 2026-10-27 Luna answered the current Rust release from a search through the MPP proxy for 0.0019 MACH. `mcp_servers` adds Streamable HTTP MCP servers (`name`, `url`, `headers`, `bearer_token`, and `paid` to answer their `-32042` payment requests from the wallet through mpp-rs's `McpPayment`) and, on macOS, servers that run as local commands over stdio (`command`, the program and its arguments, and `env`), whose tools `nanocode_mcp_tools::Mcp::prepared_servers` lists in full, signing in with OAuth when a server asks for it: `mcp_sign_in` (a server's `name`, `url` and `headers`) returns the authorization page from the SDK's `McpHandle::login`, and `mcp_sign_in_wait` waits for its loopback redirect and returns how many tools the server now offers; sessions opened after it use the token, refreshed by the SDK. Credentials reach Swift as `mcp_credentials` calls (`load` and `save`), which `McpCredentials` keeps in the Keychain (service `xyz.nanocode.mcp`). `paid_tools` adds Mercator's and the Tempo gateway's as paid servers; on 2026-10-27 they offered 15 and 26 tools, which made Haiku's request cost about 0.004 MACH, so the demo turns them on only by a setting. `permission_mode` on `open` (`plan`, `read_only`, `auto` or `full_access`) puts the session's workspace and MCP tools behind `approvals::Gate`, and the `permission_mode` command changes it from the next call: Codex's workspace tools through a gated `WorkspaceToolFactory`, file tools and MCP tools wrapped one by one. Read-only commands (`ls`, `rg`, `git status` and the like) and reads run in every mode; `read_only` asks before other commands and edits, `auto` edits inside the workspace freely and runs every command, `plan` refuses commands that are not read-only and edits, and a call outside the workspace always asks. On macOS commands run under a Seatbelt profile (`sandbox.rs`, through `/usr/bin/sandbox-exec` as Codex does) that lets them read everywhere, write only in temporary folders and, in `auto`, the workspace and its git directory, and reach no network; read-only commands get the profile without the workspace, and a command an `allow` rule covers runs outside it. Simulated commands get no profile, so `auto` asks before those that are not read-only. When the sandbox refuses a write or a connection, the gate asks with kind `outside_sandbox` and runs the command again outside the sandbox if the user allows it; on 2026-10-28 Haiku 5.5 in `auto` touched a file in the workspace without asking, and `touch ~/x` and `curl` asked to leave the sandbox. An MCP tool asks once per session, every time in `plan`. Asking is an `approval` call (`kind` `command`, `edit`, `outside_workspace`, `outside_sandbox` or `mcp`, with a `suggested_rule`) that Swift answers through `NanocodeRuntime.setApprovalHandler` with `allow`, `allow_always` (a rule such as `npm test`, `npm *`, `Edit` or `mcp__linear__*`, kept for the runtime; `allow` on `open` adds saved ones) or `deny` with feedback for the model. `observe_edits` on `open` (`SessionConfiguration.observeEdits`) sends a `will_edit` call (`session_id` and the absolute `paths`) before a workspace tool edits files, in every mode and after any approval, which Swift answers through `NanocodeRuntime.setEditObserver` once the app has kept what the files held; a session with it and no `permission_mode` runs in `full_access`. `submit` and `steer` take `images` (data URLs, sent as `UserInput::Image`) and `files` (`file_data`, a data URL, and `filename`, sent as `UserInput::File`), which `Session.submit(_:images:files:)` builds from `PromptFile`s, so a PDF or a text file reaches the model as a document; on 2026-10-28 Haiku 5.5 with no tools answered from a PDF and a text file sent this way. `Chat` sends images as `UserInput::Image` data URLs, and with `Chat.workspace` set copies attached files into `<workspace>/uploads` (a taken name gets `-2`, `-3`) and adds one `Attached: <path> (<type>, <size>)` line per file to the prompt, as nanocode-ts's `attachedPrompt` does; a session that runs on a machine through the relay has no local workspace, so the demo leaves `workspace` unset there.

## Simulated shell

`shell.rs` runs nanocode-ts's simulated bash (`nanocode-ts/bash`, its `src/bash/`: the parser, the interpreter and its 118 commands, the shell the Cloudflare and Vercel demos give their sessions) over the device's real files, for iOS, where apps may not spawn processes. `scripts/build-shell.sh` takes `src/bash`, `src/internal` and the Code Mode cell prelude (`src/wasm/prelude.js` and `prelude/`) from `../nanocode-ts` at `origin/main` (`NANOCODE_TS` and `NANOCODE_TS_REF` override them; `NANOCODE_TS_REF=worktree` takes the checkout with its uncommitted changes through `git stash create` and records its `HEAD` with `"modified": true`) with `git archive`, bundles the shell with nanocode-ts's rolldown into the IIFE `Sources/Nanocode/Resources/shell/bash.js` (1.0 MB), copies the prelude beside it and records the revision in `ts-revision.json`. These files are generated: change the shell in nanocode-ts and rerun the script; only `Resources/shell/host.js` is written here. The shell's JavaScript is a resource of the `Nanocode` target, not part of the Rust library: `NanocodeRuntime` passes its directory as `shell` in `nanocode_start`'s configuration and the shell thread reads it when it starts, so a change to it rebuilds no Rust. `Host.shell` is one `Shell` per runtime, started by its first command, which compiles the bundle once and keeps its QuickJS bytecode in `<data_dir>/shell/bash-<sha256>.qjsbc` (73 ms to compile on an Apple silicon Mac, 4 ms to load): a thread (`nanocode-shell`, 32 MiB of stack) with an rquickjs runtime of its own (1 GiB memory limit), apart from Code Mode's, that evaluates `host.js`, the prelude (its lazy modules as JSON string literals in `lazySources`, as nanocode-ts's `cells.rs` writes them; so the shell has the cells' `TextEncoder`, `URL`, `Blob`, streams, `AbortController`, `crypto` and `fetch`) and the bundle, and calls `Bash.create` with a `FileSystem` of native calls (`stat`, `lstat`, `read`, `write`, `list`, `mkdir`, `remove`, `rename`, `chmod`, `utimes`, `symlink` and `readlink`, failing with POSIX codes such as `ENOENT` and `EACCES`). Paths are the real absolute paths, except that on iOS `/tmp` is the app's temporary directory (`files::local`, which `NativeFiles` uses too); `HOME` comes from the environment, the default directory is `<data_dir>/workspace` and `maxMemoryBytes` is 256 MiB. `CompressionStream` and `DecompressionStream` (`gzip`, `deflate`, `deflate-raw`, for `gzip`, `tar -z`, `zip` and `git clone`) stream through flate2, the prelude's `crypto` hashes and draws random bytes through `__nanocodeBytes.digest` and `random`, which `shell.rs` gives it as the SDK's Code Mode engine does (SHA-1 and SHA-2, `rand`; `sha256sum`, git, `/dev/urandom`, `uuidgen`, `mktemp`), the bundle's text codec (`Bash.Codec`, UTF-8 with each byte that is not valid UTF-8 as U+DC80..U+DCFF) is native: `__shell.escaped` writes the bytes as WTF-8, those bytes as three-byte surrogates, and makes the string with `JS_NewStringLen`, which decodes surrogates, and `unescaped` reads a string's WTF-8 (`to_cstring`) back with those code units as their bytes and other lone surrogates as U+FFFD, as the bundle's `encode` does, and base64 goes through `__nanocodeBytes.toBase64` and `__shell.fromBase64` (`atob`'s forgiving decoding), `fetch` (`curl`, `wget`, `git clone`) goes through reqwest on the tokio runtime and honors `redirect: manual`, and timers run on the thread's own loop. QuickJS has no WebAssembly, so `src/shell/wasm.rs` gives the shell one: `host.js` defines `WebAssembly` (`Module`, `Instance`, `Memory`, `Table`, `Global`, `compile`, `instantiate`, `validate` and the error classes) over wasmi 2.0, the interpreter nanocode-ts compiles into its `interpreter.wasm`, with the same features, so the shell's `wasm`, `wasmtime`, `.wasm` programs (WASI in the bundle's JavaScript), `wat2wasm` and `wasm --invoke` take the bundle's native-engine path. Each instance has its own wasmi `Store` (1 GiB of memory at most); imports call back into QuickJS with the exception a JavaScript import throws (WASI's `proc_exit`) carried through the WebAssembly frames; `memory.buffer` is an `ArrayBuffer` over the instance's linear memory itself (`JS_NewArrayBuffer` with the store kept alive by the buffer), detached and replaced when the memory moves; and `Table.set` with another instance's export, which the bundle's timeout instrumentation needs, becomes a host function in this instance's store. Instrumented modules stop at the run's timeout as in V8; a `timeout N` around a program cannot fire while it runs, since the thread's timers wait for it, also as in V8. The `wasm` commands see the real files through the bundle's snapshot of the working directory and the paths named on the command line: `host.js` passes `wasm: { rootDepth: -1 }`, so the snapshot does not also read `/` two levels deep, which on a real disk meant `/.file` (EACCES on macOS) and every file under `/bin` and `/usr/bin` up to 64 MiB, and an entry the disk refuses is left out of the snapshot. wasmi is built with one codegen unit (`[profile.release.package.wasmi*]`): with the crate's `lto = "off"` and 16 units its tail-call dispatch overflowed the stack and its loop dispatch ran 4× slower. `python`, `python3`, `pip` and `pip3` run Pyodide when the app runs a `PythonHost` (`Sources/Nanocode/Python.swift`, which calls `NanocodeRuntime.setPythonHost`; without one a run fails with "this app runs no Python"): Pyodide cannot run on wasmi (its module uses the exception-handling proposal, which wasmi lacks), so it runs in a hidden `WKWebView`, where WebKit compiles it, with nanocode-ts's Python glue (`HELPER` of `src/bash/internal/commands/python.ts`: `run`, interrupts, `pip` through micropip), which `scripts/build-shell.sh` bundles into `Sources/Nanocode/Resources/python.js`; `Resources/pyodide-host.js` is written here. ## Machine payments

`payments.rs` is gakonst/nanocode-machines's `nanocode-mpp` layer moved into a library: `Mpp` is a `nanocode::http::Layer` that runs mpp-rs's 402 flow (`send_with_exchange` over the layer's `Next`) against `openai.mpp.tempo.xyz` and `anthropic.mpp.tempo.xyz`, preconnects each service once per wallet, keeps prepaid vouchers (`PREPAID_REQUESTS`), and attaches an `EventHook` that hands `payment-need-voucher` and `payment-receipt` SSE events to the session provider, which consumes them so neither backend's parser sees them. Channels live in `<data_dir>/payments/channels.db`, or in the Tempo CLI's shared store when the wallet is the CLI's. Spend comes from mpp-rs's `ClientEvents` and reaches Swift as `payments` messages (`PaymentStatus`). Without a wallet a paid request fails before it is sent with `tempo_wallet_required`.

A wallet is either the Tempo CLI's (`wallet_cli`, `TempoAccountsWallet::try_from_default_store`, macOS) or an access key the app's own Tempo Wallet approved: `wallet_connect` generates a secp256k1 key and runs the Accounts SDK's device-code exchange natively (`https://wallet.tempo.xyz/api/auth/device/register` with a PKCE challenge and an `rpc-requests` envelope holding `wallet_connect` with `authorizeAccessKey`, then `/token` polls), with nanocode-ts's limits (2 MACH and 0.1 USDC.e for fees, one day) and scopes (MACH transfers and its swapper approval, the swapper, and the TIP-1034 escrow's open, top-up, close and withdraw). The prompt (`user_code`, `verification_uri`) reaches Swift as a `wallet` message; the approved record returns to Swift, which keeps it in the Keychain (`Wallet`, service `xyz.nanocode.wallet`) and installs it with `wallet_use` on later launches. mpp-rs attaches the key's authorization to its first transaction, so no separate publication is needed.

## Build

Install Rust 1.97 or newer with the Apple targets in `rust-toolchain.toml`, Xcode 26 and XcodeGen. Run `scripts/build-ffi.sh`, then `swift build` or `xcodebuild` (for the simulator pass `ARCHS=arm64` unless the library was built with `UNIVERSAL=1`). Keep `Cargo.lock` on the SDK's versions of shared crates: libc 0.2.191 dropped `SYSPROTO_CONTROL` for iOS, which portable-pty's nix 0.28 needs, so it stays at the SDK's 0.2.186. `.github/workflows/release.yml` (run by hand: on 2026-10-27 GitHub refused to start macOS jobs for this private repository over its spending limit, so `scripts/publish-ffi.sh --upload` was run locally, with `UNIVERSAL=0` for an arm64-only build while the disk was nearly full) runs `scripts/publish-ffi.sh --upload`: it fingerprints the Rust inputs, builds a universal release XCFramework when no `ffi-<fingerprint>` release exists, uploads it with its `ffi-release.json`, and commits that file, so a consumer pins the commit that names the build. `.cargo/config.toml` routes rustc through the SDK's `scripts/buildcache`, so a checkout that shares `~/.cache/nanocode/build` with the SDK reuses its compiled crates, and sets the macOS and iOS deployment targets.
