# Development

This repository is nanocode-swift (gakonst/nanocode-swift): the nanocode Rust SDK compiled into a static library for Apple platforms, the Swift package that drives it, SwiftUI views with AppKit and UIKit hosts, and example apps for macOS and iOS, so an app writes only Swift and builds no Rust beyond `scripts/build-ffi.sh`. It follows gakonst/nanocode-ts: that package compiles the SDK into one WebAssembly module and a TypeScript host supplies SQL, HTTP, sockets and tools; here the SDK runs natively inside the app, so it keeps its own HTTPS and WebSocket transports (reqwest and tokio-tungstenite with the platform verifier), its own SQLite file, its own QuickJS Code Mode engine and, on macOS, its own shell tools, and Swift supplies only configuration, host tools, credentials and the UI. Its sibling `../nanocodex` supplies the SDK; `sdk-revision.json` records the SDK master revision this package builds against. Generic agent, durability, turn, event, hand and payment logic belongs in the SDK or in mpp-rs, host-agnostic bridge glue in `src/*.rs` and `Sources/Nanocode`, views in `Sources/NanocodeUI`, and an application's business logic (its tools, prompts, skins) in the app.

Do not add code comments, README files, Cargo features, tests or test-only dependencies. Validate changes by building the XCFramework, `swift build`, the example apps with `xcodebuild`, and runs of `Examples/Console`. The Rust side keeps state lock-free with `nanocode-sync` (`Atom`, `Slot`) as the SDK requires; Swift guards its small shared tables with `OSAllocatedUnfairLock`.

## Layout

- `src/` is the crate `nanocode-swift` (`staticlib`): `bridge.rs` is the C ABI and its multi-threaded tokio runtime, `command.rs` the command table, `session.rs` the SDK's `TurnInbox` per open session over `nanocode_store_sqlite::SqliteSql` (one `nanocode.sqlite` in the app's data directory holds every session's `SqlStore` state and `SessionLog`), `config.rs` the session configuration and model clients, `tools.rs` Swift host tools as the SDK's `FunctionTool`, `files.rs` a native `FileHost` for file tools, `hand.rs` hands, `payments.rs` and `wallet.rs` machine payments, and `catalog.rs` the model catalog.
- `include/` holds `nanocode.h` and the `NanocodeFFI` module map; `scripts/build-ffi.sh` builds the crate for `aarch64-apple-darwin` (and `x86_64-apple-darwin` with `UNIVERSAL=1`), `aarch64-apple-ios` and `aarch64-apple-ios-sim` (and `x86_64-apple-ios`) and writes `build/NanocodeFFI.xcframework`. `PROFILE=debug` builds unoptimized libraries (370 MB for macOS arm64 on 2026-10-27), `PLATFORMS="macos"` limits the platforms.
- `Package.swift` exports `Nanocode` (Foundation and Observation only) and `NanocodeUI` (SwiftUI, with `NanocodeChatViewController` for AppKit and UIKit). `NanocodeFFI` is the local XCFramework when `build/NanocodeFFI.xcframework` exists, else the release that `ffi-release.json` names (`url`, `checksum`), so apps such as tempoxyz/pyramid depend on the package without building Rust.
- `Examples/Console` is a terminal client of `Nanocode`; `Examples/Demo` is the nanocode.xyz demo as a SwiftUI app for macOS and iOS (`project.yml` for XcodeGen, `NanocodeDemo.xcodeproj` generated from it).

## Bridge

`nanocode_start(config, length, callback, context)` starts a runtime for a data directory (`{"data_dir", "tempo_home"?}`), `nanocode_send(handle, bytes, length)` sends one command and `nanocode_stop(handle)` closes every session and hand and shuts the runtime down; it blocks, so Swift calls it from `deinit` off the main actor. Every message either way is one JSON object. Swift sends `{"id", "command": {"<name>": {fields}}}` (externally tagged, as nanocode-ts's commands) and gets `{"reply": id, "ok"}` or `{"reply": id, "error"}`; a command without `id` gets no reply. Rust sends `{"event": {"session", ...}}` (`logged` and `live` batches of the SDK's `LoggedEvent`s, `driving`, `turn` with the finished turn's report, `waiting`, `resumed`, `error`), `{"call": {"id", "kind": "tool", "body": {name, input, context}}}`, which Swift answers with the `reply` command, `{"hand": {"id", "event" | "stopped"}}`, `{"wallet": {"prompt"}}`, `{"payments": {"status" | "notice"}}` and `{"log"}`. The callback runs on the runtime's threads; `Router` in `Runtime.swift` resolves replies and yields events into `AsyncStream`s synchronously, so a session's events stay in log order.

Commands: `models`, `sessions` (stored root sessions, newest first), `open` (a `Configuration`, see `config.rs`, which denies unknown fields), `close`, `submit`, `steer`, `move_queued`, `replace`, `cancel`, `turn`, `pending`, `page`, `settings`, `compact`, `settle`, `interrupt_subagent`, `close_subagent`, `reply`, `hand_start`, `hand_stop`, `hand_status`, `wallet_connect`, `wallet_use`, `wallet_cli`, `wallet_forget`, `payments` and `funding_url`. `open` builds one `Nanocode` runtime per session (`without_runners`, the session's workspace or `<data_dir>/workspace`) and opens its `TurnInbox`; a driver task per session calls `TurnInbox::drive` whenever a submit wakes it, retries `Waiting` and `Interrupted` turns with a backoff from 0.5 s to 30 s, and reports each finished turn.

## Sessions and tools

A session's provider is `claude` or `codex` with any model its harness serves (Haiku 5.5 and Luna by default). `auth` is `"tempo"` (machine payments, the default), `{"api_key"}` or `{"headers"}`; `endpoint` replaces the provider's base URL. Workspace tools follow nanocode-ts's `workspace_tools`: `all` gives the SDK's native workspace tools (shell, files, Code Mode) on macOS, and on iOS, where apps may not spawn processes, it means `files`: Claude's `Read`, `Edit` and `Write` or Codex's `apply_patch` and `view_image` over `NativeFiles`. Code Mode cells run in the SDK's native QuickJS engine on both platforms. Host tools (`HostTool` in Swift: name, description, JSON Schema parameters, `content` for text-and-image results) become `FunctionTool`s offered directly and inside Code Mode; `ToolResult.content` answers with `input_text` and `input_image` items. Claude sessions get the SDK's `WebSearch` (a nested Messages request through the same client, so it is paid the same way) unless `web_search` is false. `paid_tools` adds Mercator's and the Tempo gateway's MCP tools, paid from the wallet.

## Machine payments

`payments.rs` is gakonst/nanocode-machines's `nanocode-mpp` layer moved into a library: `Mpp` is a `nanocode::http::Layer` that runs mpp-rs's 402 flow (`send_with_exchange` over the layer's `Next`) against `openai.mpp.tempo.xyz` and `anthropic.mpp.tempo.xyz`, preconnects each service once per wallet, keeps prepaid vouchers (`PREPAID_REQUESTS`), and attaches an `EventHook` that hands `payment-need-voucher` and `payment-receipt` SSE events to the session provider, which consumes them so neither backend's parser sees them. Channels live in `<data_dir>/payments/channels.db`, or in the Tempo CLI's shared store when the wallet is the CLI's. Spend comes from mpp-rs's `ClientEvents` and reaches Swift as `payments` messages (`PaymentStatus`). Without a wallet a paid request fails before it is sent with `tempo_wallet_required`.

A wallet is either the Tempo CLI's (`wallet_cli`, `TempoAccountsWallet::try_from_default_store`, macOS) or an access key the app's own Tempo Wallet approved: `wallet_connect` generates a secp256k1 key and runs the Accounts SDK's device-code exchange natively (`https://wallet.tempo.xyz/api/auth/device/register` with a PKCE challenge and an `rpc-requests` envelope holding `wallet_connect` with `authorizeAccessKey`, then `/token` polls), with nanocode-ts's limits (2 MACH and 0.1 USDC.e for fees, one day) and scopes (MACH transfers and its swapper approval, the swapper, and the TIP-1034 escrow's open, top-up, close and withdraw). The prompt (`user_code`, `verification_uri`) reaches Swift as a `wallet` message; the approved record returns to Swift, which keeps it in the Keychain (`Wallet`, service `xyz.nanocode.wallet`) and installs it with `wallet_use` on later launches. mpp-rs attaches the key's authorization to its first transaction, so no separate publication is needed.

Measured on 2026-10-27 with the Tempo CLI wallet: `Examples/Console` asked Haiku 5.5 to call a Swift `clock` tool from Code Mode and answer, which cost 0.002182 MACH, and Luna 0.001169 MACH.

## Hands

`hand_start` runs `nanocode::hand::Hand::connect` inside the app: on macOS with the SDK's hand tools (Claude's and Codex's workspace tools over a directory), elsewhere with both providers' file tools, plus the app's host tools, so a brain such as a nanocode.xyz session or Pyramid can run Code Mode cells and tools on the phone or Mac. `hand_status` reports `HandActivity::items()` (cells, calls, tasks with their silence) and every `HandEvent` reaches Swift. `HandConfiguration.parse(command:)` reads the `nc hand '<url>' --token <token>` line the demos print.

## Build

Install Rust 1.97 or newer with the Apple targets in `rust-toolchain.toml`, Xcode 26 and XcodeGen. Run `scripts/build-ffi.sh`, then `swift build` or `xcodebuild`. `.cargo/config.toml` routes rustc through the SDK's `scripts/buildcache`, so a checkout that shares `~/.cache/nanocode/build` with the SDK reuses its compiled crates, and sets the macOS and iOS deployment targets.
