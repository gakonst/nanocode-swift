# Development

This repository is nanocode-swift (gakonst/nanocode-swift): the nanocode Rust SDK compiled into a static library for Apple platforms, the Swift package that drives it, native AppKit and UIKit views, and example apps for macOS and iOS, so an app writes only Swift and builds no Rust beyond `scripts/build-ffi.sh`. It follows gakonst/nanocode-ts: that package compiles the SDK into one WebAssembly module and a TypeScript host supplies SQL, HTTP, sockets and tools; here the SDK runs natively inside the app, so it keeps its own HTTPS and WebSocket transports (reqwest and tokio-tungstenite with the platform verifier), its own SQLite file, its own QuickJS Code Mode engine and, on macOS, its own shell tools, and Swift supplies only configuration, host tools, credentials and the UI. Its sibling `../nanocodex` supplies the SDK; `sdk-revision.json` records the SDK master revision this package builds against. Generic agent, durability, turn, event, hand and payment logic belongs in the SDK or in mpp-rs, host-agnostic bridge glue in `src/*.rs` and `Sources/Nanocode`, views in `Sources/NanocodeKit`, and an application's business logic (its tools, prompts, skins) in the app.

Do not add code comments, Cargo features, tests or test-only dependencies. `README.md` is the repository's homepage: the overview, products, quickstart and the demo recordings in `assets/` (GIFs of the demo app made with the `-NanocodeType`, `-NanocodeWindow` and `-NanocodeAppearance` launch arguments, optimized with `gifsicle -O3 --lossy=60`); development guidance stays here. Validate changes by building the XCFramework, `swift build`, the example apps with `xcodebuild`, and runs of `Examples/Console`. The Rust side keeps state lock-free with `nanocode-sync` (`Atom`, `Slot`) as the SDK requires; Swift guards its small shared tables with `OSAllocatedUnfairLock`.

## Layout

- `src/` is the crate `nanocode-swift` (`staticlib`): `bridge.rs` is the C ABI and its multi-threaded tokio runtime, `command.rs` the command table, `session.rs` the SDK's `TurnInbox` per open session over `nanocode_store_sqlite::SqliteSql` (one `nanocode.sqlite` in the app's data directory holds every session's `SqlStore` state and `SessionLog`), `config.rs` the session configuration and model clients, `tools.rs` Swift host tools as the SDK's `FunctionTool`, `files.rs` a native `FileHost` for file tools, `hand.rs` hands, `payments.rs` and `wallet.rs` machine payments, and `catalog.rs` the model catalog.
- `include/` holds `nanocode.h` and the `NanocodeFFI` module map; `scripts/build-ffi.sh` builds the crate for `aarch64-apple-darwin` (and `x86_64-apple-darwin` with `UNIVERSAL=1`), `aarch64-apple-ios` and `aarch64-apple-ios-sim` (and `x86_64-apple-ios`) and writes `build/NanocodeFFI.xcframework`. `PROFILE=debug` builds unoptimized libraries (370 MB for macOS arm64 on 2026-10-27), `PLATFORMS="macos"` limits the platforms.
- `NanocodeKit` is the UI, in AppKit on macOS and UIKit on iOS from one source (`KitView`, `KitColor` and `KitFont` alias the platform types; no SwiftUI): `CloneViewController` and `CloneNode` are nanocode-ts's ChatGPT and Claude clone apps (`src/react/clones/chatgpt.tsx`, `claude.tsx` and their CSS, as nanocode-vercel-durable's `/chatgpt` and `/claude` render them) with `Skin.chatgpt` and `Skin.claude` carrying their CSS variables in light and dark: the sidebar of chats with hover rows and delete, the header (ChatGPT's model menu, Claude's centered title), the hero with the greeting, composer, prompt pills and footer, the transcript (user bubble, grouped tool calls as ChatGPT's "Ran code" card or Claude's collapsed cells, thinking blocks, markdown with code bars and ruled tables, the pulse or spinning spark), the composer with attachments, steer and stop, and the model list, which opens below the ChatGPT header and above the Claude composer. `CloneProps` carries what the host supplies (conversations and callbacks, `ClonePicker`, prompts, footer markdown, header actions such as a `ClonePill`, `titlebarInset` for a full-size-content window). Below 768 points wide the layout follows the clones' mobile CSS: the sidebar becomes a drawer over a scrim, the header shows its open and new-chat buttons, the user bubble widens to 85% and the hero shrinks; on iOS it keeps to the safe area and above the keyboard. `NanocodeChatViewController` is the conversation alone for an app's own window. Views are `Node` subclasses that measure and place their children themselves (`Stack`, `Flow`, `Label`, `TextNode` on `NSTextView`/`UITextView` for selectable text, `ScrollNode`, `InputNode`), and `Observer` re-renders on `Chat`'s Observation changes. Check layouts at phone width with the demo's `-NanocodeWindow 390x844` (`-NanocodeBackground YES` keeps it from taking focus, `-NanocodeNew YES` opens a new chat, `-NanocodeStyle chatgpt|claude`, `-NanocodeAppearance light|dark`, and `-NanocodeType YES` types `-NanocodePrompt` into the composer before sending it, for recordings).
- `Package.swift` exports four products. `NanocodeCore` is plain Swift with no Rust: `JSON`, `LoggedEvent`, `LiveEvent` (nanocode-ts's `liveEvent`, plus `user` events from `input.accepted`), `Transcript` (nanocode-ts's `Transcript`: paced reveal, paragraphs, one `ToolCell` per call with nested Code Mode calls, yielded cells and their `wait`s), `ToolInput`, `Turn.group`, `Activity`, the markdown block parser with `MarkdownStream`, `Highlight`'s tokenizer and `DataURL`. `NanocodeViews` is SwiftUI over it, also without Rust, kept for SwiftUI hosts such as tempoxyz/pyramid's app; this package's own UI and apps are AppKit and UIKit (`NanocodeKit`): `MarkdownView` with `MarkdownStream` and `Highlight` (ported from tempoxyz/pyramid's transcript), `CodeBlock`, `ToolCellView`, `ThinkingView`, `TranscriptView` over a `TranscriptState`, and `NanocodeTheme`. `Nanocode` is the runtime over the Rust library (`NanocodeRuntime`, `Session`, `Chat`, `Wallet`, `WalletMonitor`, `HandMonitor`, hands, runners, the model catalog). A host that renders nanocode events it receives some other way, such as from a server, uses only `NanocodeCore` and `NanocodeViews` and links no Rust. `NanocodeFFI` is the local XCFramework when `build/NanocodeFFI.xcframework` exists, else the release that `ffi-release.json` names (`url`, `checksum`, `fingerprint`), so apps such as tempoxyz/pyramid depend on the package without building Rust; the repository is private, so SwiftPM needs GitHub credentials (a `~/.netrc` entry for `github.com`) to download it.
- `Examples/Console` is a terminal client of `Nanocode`: a prompt (`NANOCODE_PROVIDER`, `NANOCODE_MODEL`, an API key from `ANTHROPIC_API_KEY` or `OPENAI_API_KEY`, else the Tempo CLI wallet, and `NANOCODE_RELAY_TOKEN` to take a machine through the relay), or `Console hand|runner <url> <token> [name]` to make the process a hand or attachment runner. `Examples/Demo` is the nanocode.xyz demo as an AppKit app for macOS and a UIKit app for iOS, in the ChatGPT or Claude style (View menu, ⌘1 and ⌘2, or Settings) (`project.yml` for XcodeGen; run `xcodegen generate` there, the project is not committed): conversations from the store, a model menu, a Tempo Wallet card, device tools (`device_info`, `open_url`, `clipboard`, `speak`), a computer connected through the relay, and this device as a hand. Launch arguments script it for checks: `-NanocodeWallet cli`, `-NanocodeProvider`, `-NanocodeModel` and `-NanocodePrompt`. The same project builds `NanocodeAppKit-macOS` (`AppKit/main.swift`, an `NSWindow` around `NanocodeChatViewController`) and `NanocodeUIKit-iOS` (`UIKit/AppDelegate.swift`, a `UINavigationController` around it with the wallet in a sheet), the smallest hosts of `NanocodeKit`'s `NanocodeChatViewController`. Device builds need `DEVELOPMENT_TEAM` (`xcodebuild ... DEVELOPMENT_TEAM=<team>`); `CODE_SIGNING_ALLOWED=NO` checks that they compile. This Xcode had no simulator runtime or `simctl` on 2026-10-27, so the iOS apps were compiled for the simulator and devices but not run.

## Bridge

`nanocode_start(config, length, callback, context)` starts a runtime for a data directory (`{"data_dir", "tempo_home"?}`), `nanocode_send(handle, bytes, length)` sends one command and `nanocode_stop(handle)` closes every session and hand and shuts the runtime down; it blocks, so Swift calls it from `deinit` off the main actor. Every message either way is one JSON object. Swift sends `{"id", "command": {"<name>": {fields}}}` (externally tagged, as nanocode-ts's commands) and gets `{"reply": id, "ok"}` or `{"reply": id, "error"}`; a command without `id` gets no reply. Rust sends `{"event": {"session", ...}}` (`logged` and `live` batches of the SDK's `LoggedEvent`s, `driving`, `turn` with the finished turn's report, `waiting`, `resumed`, `error`), `{"call": {"id", "kind": "tool", "body": {name, input, context}}}`, which Swift answers with the `reply` command, `{"hand": {"id", "event" | "stopped"}}` and `{"runner": ...}` alike, `{"wallet": {"prompt"}}`, `{"payments": {"status" | "notice"}}` and `{"log"}`. The callback runs on the runtime's threads; `Router` in `Runtime.swift` resolves replies and yields events into `AsyncStream`s synchronously, so a session's events stay in log order.

Commands: `models`, `sessions` (stored root sessions, newest first), `open` (a `Configuration`, see `config.rs`, which denies unknown fields), `close`, `submit`, `steer`, `move_queued`, `replace`, `cancel`, `turn`, `pending`, `page`, `settings`, `compact`, `checkpoint`, `permission_mode`, `settle`, `interrupt_subagent`, `close_subagent`, `reply`, `hand_start`, `hand_stop`, `hand_status`, `runner_start`, `runner_stop`, `runner_status`, `wallet_connect`, `wallet_use`, `wallet_cli`, `wallet_forget`, `payments` and `funding_url`. `open` builds one `Nanocode` runtime per session (`without_runners`, the session's workspace or `<data_dir>/workspace`) and opens its `TurnInbox`; a driver task per session calls `TurnInbox::drive` whenever a submit wakes it, retries `Waiting` and `Interrupted` turns with a backoff from 0.5 s to 30 s, and reports each finished turn. An `open` with `fork` (`session`, an open session's id) starts a new session from that one's conversation through `Runtime::switch`, which forks it when the configuration keeps the model and otherwise carries its transcript to the configuration's model or provider; with `checkpoint` (from the `checkpoint` command, taken before a turn) and `before` (that turn's request id) it forks the conversation as it was before that turn. The new session gets its own ID, which the reply carries, a copy of the parent's log up to the fork point, and a place in `sessions`.

## Sessions and tools

A session's provider is `claude` or `codex` with any model its harness serves (Haiku 5.5 and Luna by default). `auth` is `"tempo"` (machine payments, the default), `{"api_key"}` or `{"headers"}`; `endpoint` replaces the provider's base URL. Workspace tools follow nanocode-ts's `workspace_tools`: `all` gives the SDK's native workspace tools (shell, files, Code Mode) on macOS, and on iOS, where apps may not spawn processes, it means `files`: Claude's `Read`, `Edit` and `Write` or Codex's `apply_patch` and `view_image` over `NativeFiles`. Code Mode cells run in the SDK's native QuickJS engine on both platforms. Host tools (`HostTool` in Swift: name, description, JSON Schema parameters, `content` for text-and-image results) become `FunctionTool`s offered directly and inside Code Mode; `ToolResult.content` answers with `input_text` and `input_image` items. Claude sessions get the SDK's `WebSearch` (a nested Messages request through the same client, so it is paid the same way) and Codex sessions the SDK's host `web__run` (a nested Responses request with OpenAI's `web_search` tool) over `payments::Transport`, a `HostTransport` that sends it through the session's layer (machine payments, the API key or the configured headers), unless `web_search` is false. On 2026-10-27 Luna answered the current Rust release from a search through the MPP proxy for 0.0019 MACH. `mcp_servers` adds Streamable HTTP MCP servers (`name`, `url`, `headers`, `bearer_token`, and `paid` to answer their `-32042` payment requests from the wallet through mpp-rs's `McpPayment`), whose tools `nanocode_mcp_tools::Mcp::prepared_servers` lists in full, and `paid_tools` adds Mercator's and the Tempo gateway's as paid servers; on 2026-10-27 they offered 15 and 26 tools, which made Haiku's request cost about 0.004 MACH, so the demo turns them on only by a setting. `permission_mode` on `open` (`plan`, `read_only`, `auto` or `full_access`) puts the session's workspace and MCP tools behind `approvals::Gate`, and the `permission_mode` command changes it from the next call: Codex's workspace tools through a gated `WorkspaceToolFactory`, file tools and MCP tools wrapped one by one. Read-only commands (`ls`, `rg`, `git status` and the like) and reads run in every mode; `read_only` asks before other commands and edits, `auto` edits inside the workspace freely, `plan` refuses commands that are not read-only and edits, and a call outside the workspace always asks. An MCP tool asks once per session, every time in `plan`. Asking is an `approval` call (`kind` `command`, `edit`, `outside_workspace` or `mcp`, with a `suggested_rule`) that Swift answers through `NanocodeRuntime.setApprovalHandler` with `allow`, `allow_always` (a rule such as `npm test`, `npm *`, `Edit` or `mcp__linear__*`, kept for the runtime; `allow` on `open` adds saved ones) or `deny` with feedback for the model. `Chat` sends images as `UserInput::Image` data URLs, and with `Chat.workspace` set copies attached files into `<workspace>/uploads` (a taken name gets `-2`, `-3`) and adds one `Attached: <path> (<type>, <size>)` line per file to the prompt, as nanocode-ts's `attachedPrompt` does; a session that runs on a machine through the relay has no local workspace, so the demo leaves `workspace` unset there.

## Machine payments

`payments.rs` is gakonst/nanocode-machines's `nanocode-mpp` layer moved into a library: `Mpp` is a `nanocode::http::Layer` that runs mpp-rs's 402 flow (`send_with_exchange` over the layer's `Next`) against `openai.mpp.tempo.xyz` and `anthropic.mpp.tempo.xyz`, preconnects each service once per wallet, keeps prepaid vouchers (`PREPAID_REQUESTS`), and attaches an `EventHook` that hands `payment-need-voucher` and `payment-receipt` SSE events to the session provider, which consumes them so neither backend's parser sees them. Channels live in `<data_dir>/payments/channels.db`, or in the Tempo CLI's shared store when the wallet is the CLI's. Spend comes from mpp-rs's `ClientEvents` and reaches Swift as `payments` messages (`PaymentStatus`). Without a wallet a paid request fails before it is sent with `tempo_wallet_required`.

A wallet is either the Tempo CLI's (`wallet_cli`, `TempoAccountsWallet::try_from_default_store`, macOS) or an access key the app's own Tempo Wallet approved: `wallet_connect` generates a secp256k1 key and runs the Accounts SDK's device-code exchange natively (`https://wallet.tempo.xyz/api/auth/device/register` with a PKCE challenge and an `rpc-requests` envelope holding `wallet_connect` with `authorizeAccessKey`, then `/token` polls), with nanocode-ts's limits (2 MACH and 0.1 USDC.e for fees, one day) and scopes (MACH transfers and its swapper approval, the swapper, and the TIP-1034 escrow's open, top-up, close and withdraw). The prompt (`user_code`, `verification_uri`) reaches Swift as a `wallet` message; the approved record returns to Swift, which keeps it in the Keychain (`Wallet`, service `xyz.nanocode.wallet`) and installs it with `wallet_use` on later launches. mpp-rs attaches the key's authorization to its first transaction, so no separate publication is needed.

Measured on 2026-10-27 with the Tempo CLI wallet: `Examples/Console` asked Haiku 5.5 to call a Swift `clock` tool from Code Mode and answer, which cost 0.002182 MACH, and Luna 0.001169 MACH.

## Hands

`hand_start` runs `nanocode::hand::Hand::connect` inside the app: on macOS with the SDK's hand tools (Claude's and Codex's workspace tools over a directory), elsewhere with both providers' file tools, plus the app's host tools, so a brain such as a nanocode.xyz session or Pyramid can run Code Mode cells and tools on the phone or Mac. `hand_status` reports `HandActivity::items()` (cells, calls, tasks with their silence) and every `HandEvent` reaches Swift. `HandConfiguration.parse(command:)` reads the `nc hand '<url>' --token <token>` line the demos print. `runner_start` serves the same tools over the attachment protocol instead (`Tools::attach` with `AttachmentMetadata::machine`), which tempoxyz/pyramid's broker speaks, so Pyramid for Mac can run its Hand in the app process; `runner_stop` detaches and `runner_status` reports each runner's `AttachmentStatus`. On 2026-10-27 a nanocode CLI brain (`nanocode exec --runner-host 127.0.0.1:47291 --runner-mode replace`, Luna) ran a cell on `Console hand` that called the console's Swift `clock` tool and `exec_command`.

A session takes hands as runners: `SessionConfiguration.hands` lists `HandLink`s (`url`, `token`, `name`, `mode` `alongside` or `replace`), which `open` passes to `RuntimeBuilder::runner`, so the SDK's `RunnerPool` dials them and offers the `hands` tool; sessions without hands are built `without_runners`. Plaintext runner listeners are loopback only, so a brain on a phone or a Mac takes another machine's hand through a relay: `HandRelay` pairs both by a random 32-hex-digit token at the Cloudflare demo's `HandRelay` Durable Object (`https://nanocode.xyz/cloudflare/relay`, gakonst/nanocode-ts `src/cloudflare/relay.ts`), `command` is the `curl -fsSL https://nanocode.xyz/install | sh -s -- hand 'wss://nanocode.xyz/cloudflare/relay' --token <token>` line the machine runs, `hands()` asks the relay which hands are attached, and `brain()` is the link the session dials (`?role=brain&wait`, `replace` by default, because a hand's own tools reach the model only as the replacement executor). Name no link the relay serves: an explicit runner name kept the hand's catalog out of the session. The demo app polls `hands()` (every 3 s, 20 s while one is attached) and reopens its session with or without the link when a machine attaches or leaves. On 2026-10-27 the demo app on macOS (Haiku 5.5 over MPP) listed, read and ran `uname -n` on a `nanocode hand` attached through the relay.

## Build

Install Rust 1.97 or newer with the Apple targets in `rust-toolchain.toml`, Xcode 26 and XcodeGen. Run `scripts/build-ffi.sh`, then `swift build` or `xcodebuild` (for the simulator pass `ARCHS=arm64` unless the library was built with `UNIVERSAL=1`). Keep `Cargo.lock` on the SDK's versions of shared crates: libc 0.2.191 dropped `SYSPROTO_CONTROL` for iOS, which portable-pty's nix 0.28 needs, so it stays at the SDK's 0.2.186. `.github/workflows/release.yml` (run by hand: on 2026-10-27 GitHub refused to start macOS jobs for this private repository over its spending limit, so `scripts/publish-ffi.sh --upload` was run locally, with `UNIVERSAL=0` for an arm64-only build while the disk was nearly full) runs `scripts/publish-ffi.sh --upload`: it fingerprints the Rust inputs, builds a universal release XCFramework when no `ffi-<fingerprint>` release exists, uploads it with its `ffi-release.json`, and commits that file, so a consumer pins the commit that names the build. `.cargo/config.toml` routes rustc through the SDK's `scripts/buildcache`, so a checkout that shares `~/.cache/nanocode/build` with the SDK reuses its compiled crates, and sets the macOS and iOS deployment targets.

## Pyramid

What tempoxyz/pyramid's Swift app can take from here instead of keeping its own: `MarkdownView`, `MarkdownStream` and `Highlight` (its `Thread/Markdown.swift`, `MarkdownStream.swift` and `Highlight.swift`, with `NanocodeTheme` standing in for its Zyzz tokens and without its link chips and attached media), `ToolCellView` and `Transcript` for any surface that renders nanocode events, and the in-process hand: `runner_start` runs the attachment runner its `pyramid-hand` binary runs today, and `HandMonitor`/`HandStatus` replace `HandClient`'s status socket for a Hand that runs in the app. Pyramid's claim flow, served directories, pause, update and LaunchAgent stay Pyramid's.
