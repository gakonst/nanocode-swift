# Development

This repository is nanocode-swift (gakonst/nanocode-swift): the nanocode Rust SDK compiled into a static library for Apple platforms, the Swift package that drives it, native AppKit and UIKit views, and example apps for macOS and iOS, so an app writes only Swift and builds no Rust beyond `scripts/build-ffi.sh`. It follows gakonst/nanocode-ts: that package compiles the SDK into one WebAssembly module and a TypeScript host supplies SQL, HTTP, sockets and tools; here the SDK runs natively inside the app, so it keeps its own HTTPS and WebSocket transports (reqwest and tokio-tungstenite with the platform verifier), its own SQLite file, its own QuickJS Code Mode engine, its own shell tools on macOS and, on iOS, nanocode-ts's simulated bash in a QuickJS runtime of its own, and Swift supplies only configuration, host tools, credentials and the UI. Its sibling `../nanocodex` supplies the SDK; `sdk-revision.json` records the SDK master revision this package builds against, and `ts-revision.json` the nanocode-ts revision whose simulated bash and Code Mode cell prelude `src/shell/` bundles. Generic agent, durability, turn, event, hand and payment logic belongs in the SDK or in mpp-rs, host-agnostic bridge glue in `src/*.rs` and `Sources/Nanocode`, views in `Sources/NanocodeKit`, and an application's business logic (its tools, prompts, skins) in the app.

## Rules

These rules come from gakonst/nanocode's `AGENTS.md` and apply to every change here.

- Do not add code comments, doc comments, or comment headers. Names, types, and this file carry what a reader needs. Only comments that a tool reads stay, such as `// swift-tools-version` in `Package.swift`.
- Do not add tests, test targets, Cargo features, or test-only dependencies. Validate a change by building the XCFramework, `swift build`, the example apps with `xcodebuild`, and runs of `Examples/Console`, and record the commands and results here.
- `README.md` is the repository's homepage: the overview, products, quickstart and the demo recordings in `assets/` (GIFs of the demo app made with the `-NanocodeType`, `-NanocodeWindow` and `-NanocodeAppearance` launch arguments, optimized with `gifsicle -O3 --lossy=60`). Development guidance belongs in this file.
- Keep logs, traces, raw recordings, and scratch files in ignored `output/`. Never commit credentials or personal test data.
- Record what a change establishes in this file: the behavior, the reason the code cannot show, and the commands, inputs, dates, and before and after measurements. Correct or remove the entries that the change makes stale, so this file stays a description of the current code.
- The Rust side keeps state lock-free with `nanocode-sync` (`Atom`, `Slot`) as the SDK requires. Swift guards its small shared tables with `OSAllocatedUnfairLock`.
- Prefer simple code and small changes. Preserve unrelated work.
- Take every limit from a real platform or protocol constraint, a measured requirement, or explicit caller policy, and record its source here. Surface invalid states instead of hiding them with silent truncation, clamping, or fallback values.
- Benchmark performance changes with reproducible commands and inputs, and report before and after results. Keep cold builds, incremental builds, and runtime performance separate.
- Keep the development loop fast: build only what changed, reuse caches, and skip redundant checks. Honor requests to skip builds or CI.
- Work in the main checkout on `main` and push each completed change to `main`. Do not create worktrees or feature branches. Commit only your own changes, leave other dirty or untracked files alone, and rebase onto `origin/main` when a push is rejected.

## Layout

- `src/` is the crate `nanocode-swift` (`staticlib`): `bridge.rs` is the C ABI and its multi-threaded tokio runtime, `command.rs` the command table, `session.rs` the SDK's `TurnInbox<SessionLog<_>>` per open session over `sqlite.rs`'s `SqliteSql` (one `nanocode.sqlite` in the app's data directory holds every session's `SqlStore` state and `SessionLog`; the SDK dropped its SQLite host on 2026-11-08 in d326d01f0, when pyramid-core was its only remaining SQL user, so this crate keeps the last version of that host, `open_async` only, over rusqlite 0.38 with bundled SQLite, and existing `nanocode.sqlite` files open unchanged), `config.rs` the session configuration and model clients, `tools.rs` Swift host tools as the SDK's `FunctionTool`, `files.rs` a native `FileHost` for file tools, `shell.rs` the simulated bash (see Simulated shell), `hand.rs` hands, `payments.rs` and `wallet.rs` machine payments, and `catalog.rs` the model catalog.
- `include/` holds `nanocode.h` and the `NanocodeFFI` module map; `scripts/build-ffi.sh` builds the crate for `aarch64-apple-darwin` (and `x86_64-apple-darwin` with `UNIVERSAL=1`), `aarch64-apple-ios` and `aarch64-apple-ios-sim` (and `x86_64-apple-ios`) and writes `build/NanocodeFFI.xcframework`. It runs one `cargo build` for every target and copies into the XCFramework only the files whose contents changed (`rsync -c`), so a Rust change leaves its headers alone and Xcode relinks the apps without recompiling their Swift (10.6 s for the Mac demo, against 117 s when the XCFramework was written anew). `PROFILE` is `fast` by default: release dependencies, and this crate at `opt-level` 1 with 256 codegen units and incremental compilation (`--config profile.release.package.nanocode-swift.*`, so the dependencies keep their release builds); `PROFILE=release` builds this crate at `opt-level` 3 too, as `scripts/publish-ffi.sh` does, and `PROFILE=debug` builds unoptimized libraries (370 MB for macOS arm64 on 2026-10-27). `PLATFORMS="macos"` limits the platforms. The crate is a `staticlib` only: an `rlib` beside it spent about 10 s per build writing metadata nothing reads. Measured on 2026-10-29 for one edit to `src/shell.rs` (Apple silicon, under heavy load from other builds): a release build of the crate took 34 to 65 s, 41 s of it in LLVM's passes, 21 s in code generation and 10.5 s in metadata (`-Z time-passes`), and `PLATFORMS=macos scripts/build-ffi.sh` with `fast` took 36 s including that build. SwiftPM recompiles `Nanocode` and every module above it whenever the library changes (it lists the copied `libnanocode_swift.a` as an input of each Swift compile; 21 to 23 s for `Console`), while Xcode only relinks; a Swift edit in `NanocodeKit` took 12 s to rebuild the Mac demo in Debug and 18 s in Release.
- `NanocodeKit` is the UI, in AppKit on macOS and UIKit on iOS from one source (`KitView`, `KitColor` and `KitFont` alias the platform types; no SwiftUI): `CloneViewController` and `CloneNode` are nanocode-ts's ChatGPT and Claude clone apps (`src/react/clones/ChatGpt.tsx`, `Claude.tsx` and their CSS, as nanocode-vercel-durable's `/chatgpt` and `/claude` render them) with `Skin.chatgpt` and `Skin.claude` carrying their CSS variables in light and dark: the sidebar of chats with hover rows and delete, the header (ChatGPT's model menu, Claude's centered title), the hero with the greeting, composer, prompt pills and footer, the transcript (user bubble, grouped tool calls as ChatGPT's "Ran code" card or Claude's collapsed cells, thinking blocks, markdown with code bars and ruled tables, the pulse or spinning spark), the composer with attachments, steer and stop, and the model list, which opens below the ChatGPT header and above the Claude composer. `CloneProps` carries what the host supplies (conversations and callbacks, `ClonePicker`, prompts, footer markdown, header actions such as a `ClonePill`, `titlebarInset` for a full-size-content window). Below 768 points wide the layout follows the clones' mobile CSS: the sidebar becomes a drawer over a scrim, the header shows its open and new-chat buttons, the user bubble widens to 85% and the hero shrinks; on iOS it keeps to the safe area and above the keyboard. `NanocodeChatViewController` is the conversation alone for an app's own window. Views are `Node` subclasses that measure and place their children themselves (`Stack`, `Flow`, `Label`, `TextNode` on `NSTextView`/`UITextView` for selectable text, `ScrollNode`, `InputNode`), and `Observer` re-renders on `Chat`'s Observation changes. Check layouts at phone width with the demo's `-NanocodeWindow 390x844` (`-NanocodeBackground YES` keeps it from taking focus, `-NanocodeNew YES` opens a new chat, `-NanocodeStyle chatgpt|claude`, `-NanocodeAppearance light|dark`, and `-NanocodeType YES` types `-NanocodePrompt` into the composer before sending it, for recordings).
- `NanocodeDevice` (iOS and macOS; its sources are `#if os(iOS) || os(macOS)`) is an iPhone's or a Mac's tools and permissions for a hand, moved from gakonst/personal's `apple/App/Hand` (2026-11-01), which had ported and expanded `Examples/Demo/Shared/DeviceTools.swift`: `DeviceTools.all` (`open_url`, `speak`, `photos`, `listen`, `compose`, `camera`, `device_info`, `clipboard`, `screen`, `shortcut`, `files`, `speech`, `contacts`, `calendar`, `reminders`, `location`, `geofence`, `notification`, `motion`, `music`, `bluetooth`, `local_network`, `photo_library`, `wallet`, and `focus`, `health`, `home` and `nfc` when the binary is signed with their entitlement, which `Entitlements` reads from the running executable's code signature) and `DeviceCapability` (one per permission: label, group, description, the tools it gates, an SF Symbol and `reason`; `all`, `available`, `open`, `groups`, `named`, `permission(name)`, `system(name)` to ask iOS, and `hand(ask:)`, the `HandCapability`s a hand offers, asking the user through `ask` before the system prompt). An app calls `DeviceTools.configure(DeviceSettings(app:hand:scheme:appGroup:buildKey:reasons:composer:))` before building the tools: `app` is the name tool text and errors use ("needs Personal open"), `hand` the hand name a permission error tells the agent to ask through, `scheme` the URL scheme `shortcut` comes back on (the app passes opened URLs to `ShortcutCallbacks.handle`), `appGroup` the container `files` calls `group`, `buildKey` the Info.plist key `device_info` reports as `app_build`, `reasons` replaces a capability's default reason, and `composer` drafts messages and email (the `compose` tool is left out without one), so an app that avoids linking MessageUI at launch, as Personal does with its lazily loaded framework, keeps doing so. The package's iOS floor is 17, so iOS 18 and 26 APIs the tools used (`HKUnit.appleEffortScore`, `PKPass.relevantDates`, MapKit's `MKReverseGeocodingRequest` and `MKMapItem.location` and `address`) are taken when available, with `CLGeocoder`, `relevantDate` and placemarks before. Built with `xcodebuild -scheme NanocodeDevice -destination 'generic/platform=iOS Simulator'` against the release FFI (with `build/` moved aside and SwiftPM's manifest cache cleared, since the manifest picks `build/NanocodeFFI.xcframework`, which this Mac builds for macOS only, whenever it exists). On macOS (2026-11-01) the same tools build with AppKit where iOS uses UIKit (`DevicePresenter` is `UIViewController` or `NSWindow`, `DeviceTools.top()` the key window, `open` through `NSWorkspace`, the clipboard through `NSPasteboard`, `files`' pick, export and share through `NSOpenPanel`, `NSSavePanel` and `NSSharingServicePicker`, `shortcut` checks `NSWorkspace.urlForApplication`), and leave out what a Mac lacks: `camera`, `screen`, `motion`, `music`, `wallet`, `health`, `home` and `nfc` and their capabilities (`Health`, `Home`, `Media`, `MotionTools` and `Wallet` stay `#if os(iOS)`), and `authorizedWhenInUse`, which macOS does not have, so `location` there is granted only `authorizedAlways`. Tool text names the device as `DeviceTools.here` (iPhone or Mac) and its settings as `DeviceTools.settingsApp`. `DeviceTools.environment` is the `HandEnvironment` a hand reports (`ios` with the system name, version and model; `darwin` with the OS version string). `NanocodeDeviceCompose`, a sixth product, is `DeviceComposer.system`: MessageUI's message and mail sheets on iOS and `NSSharingService`'s compose email and message services on macOS, separate so an app such as Personal that loads MessageUI lazily does not link it. `Examples/Demo` uses only these: `DeviceTools.configure(DeviceSettings(app: "Nanocode", hand:, scheme: "nanocodedemo", composer: .system))`, `DeviceTools.all` for its sessions and hands, `DeviceCapability.hand` (granting the app's own prompt, so the system's asks) and `DeviceTools.environment`; it registers `nanocodedemo` and passes opened URLs to `ShortcutCallbacks.handle`, declares the Bonjour types `local_network` browses and the always-location and local-network usage strings, and its own `DemoTools` and `DeviceTools` copies are gone. `swift build` builds both products for macOS, and `xcodebuild` built `NanocodeDemo-macOS` and `NanocodeDemo-iOS` (simulator) against the release FFI. On 2026-11-01 the signed Mac demo, attached as a hand to `nc exec --runner-host … --runner-mode alongside` (Claude Haiku 5.5), answered `device_info`, `clipboard` write, read and types, `files` containers, write, read and delete, `notification` settings, `local_network` types and `speak`, refused `location` until its permission was requested, and listed its ten capabilities as `prompt`; a `shortcut` call naming a shortcut that does not exist came back through `x-error` on `nanocodedemo://` in 809 ms with Shortcuts' own "Could not find the shortcut" text, so the callback path works on macOS. Publish a new FFI (`scripts/publish-ffi.sh --upload`, after recording the nanocodex revision in `sdk-revision.json`, since `Cargo.toml` builds the SDK from the `../nanocodex` checkout) whenever the bridge's config or exports change, and run an app against the release, not only `build/`.
- The FFI follows the SDK's master (2026-11-09: 4179b40d7, from 58f8bf4ad, four commits: `nanocode-process`'s bounded child, the sandbox's budget, `nanocode-sync`'s `Backoff::endless`, and Codex web search on the ChatGPT plan, of which the bridge uses none directly; `cargo check` and the universal release build passed with `Cargo.lock` unchanged). On 2026-11-08 it moved to 58f8bf4ad from 80b2d5a39 (245 commits). The SDK dropped what the bridge stood on: its SQLite host (kept here as `src/sqlite.rs`, above), `TurnInbox`'s SQL host parameter (it is now `TurnInbox<L>` over the log, `TurnInbox<SessionLog<Shared>>` here) and `OpenAiBuilder::http_timeouts` (the API-key Codex client is now `OpenAiBuilder::http_client` with a reqwest client that has the same 30 s connect and 300 s read timeouts). Hands report two more states, which `Hand.swift` maps: `moving` (dialing another brain while still serving the current one, so `connected`) and `unconfirmed` (the brain did not confirm the hand; `retrying` after `retry_ms`); `connected` also carries `dial_ms`, the dial's total time. The SDK migrates an existing `nanocode.sqlite` on open (`session_log` storage format 1 to 2), so a data directory the old FFI wrote opens unchanged and keeps its sessions, while the old FFI then refuses it ("session_log storage format 2 is newer than this release supports"). `scripts/build-shell.sh` took the shell from nanocode-ts e67234b. - `Package.swift` exports seven products (`NanocodeDevice` and `NanocodeDeviceCompose` above, `NanocodeComputer` below). `NanocodeCore` is plain Swift with no Rust: `JSON`, `LoggedEvent`, `LiveEvent` (nanocode-ts's `liveEvent`, plus `user` events from `input.accepted`), `Transcript` (nanocode-ts's `Transcript`: paced reveal, paragraphs, one `ToolCell` per call with nested Code Mode calls, yielded cells and their `wait`s), `ToolInput`, `Turn.group`, `Activity`, the markdown block parser with `MarkdownStream` (`complete`, `blocks`, and `lines`, `fences` and `test` for a host's own streaming views), `StreamingBlocks` (`blocks(complete(text))` for a reply that grows at its end, at a cost that does not grow with it: appending can only change where the last block starts, so every block before the last two is kept from the previous call and only the last is healed, and a rewrite or a link or footnote definition, which keeps a reply whole, starts over), `Highlight`'s tokenizer and `DataURL`. tempoxyz/pyramid's app takes the parser, the stream, `StreamingBlocks` and the tokenizer from here and keeps its own caches (a two-generation least-recently-used cache, so a streaming reply's versions never push finished blocks out) and its own SwiftUI views and colors. `NanocodeViews` is SwiftUI over it, also without Rust, kept for SwiftUI hosts such as tempoxyz/pyramid's app; this package's own UI and apps are AppKit and UIKit (`NanocodeKit`): `MarkdownView` with `MarkdownStream` and `Highlight` (ported from tempoxyz/pyramid's transcript), `CodeBlock`, `ToolCellView`, `ThinkingView`, `TranscriptView` over a `TranscriptState`, and `NanocodeTheme`. `Nanocode` is the runtime over the Rust library (`NanocodeRuntime`, `Session`, `Chat`, `Wallet`, `WalletMonitor`, `HandMonitor`, hands, runners, the model catalog). A host that renders nanocode events it receives some other way, such as from a server, uses only `NanocodeCore` and `NanocodeViews` and links no Rust. `NanocodeFFI` is the local XCFramework when `build/NanocodeFFI.xcframework` exists, else the release that `ffi-release.json` names (`url`, `checksum`, `fingerprint`), so apps depend on the package without building Rust. SwiftPM downloads every binary target of a dependency whether or not a product the app uses links it: an app that took only `NanocodeCore` fetched the 231 MB `NanocodeFFI.xcframework.zip` and held 880 MB in `.build` after `swift package resolve` (2026-11-05). With `NANOCODE_WITHOUT_FFI` set in the environment that resolves the package, the manifest leaves out `NanocodeFFI` and every product that links it (`Nanocode`, `NanocodeKit`, `NanocodeDevice`, `NanocodeDeviceCompose`), so a host of the FFI-free products (`NanocodeCore`, `NanocodeViews`, `NanocodeComputer`) downloads nothing: the same app then built with no `artifacts` and a 4 MB checkout. tempoxyz/pyramid sets it in its build script and CI. The repository is public since 2026-11-05, so fetching it needs no credential.
- `Examples/Console` is a terminal client of `Nanocode` (`Console remote cloudflare|vercel [prompts…]` chats with a deployment through `RemoteSession` and reopens the conversation from its journal, and `Console remote-resume [id]` follows a turn a killed process left open, and `Console bash <script>` runs a script in the simulated shell): a prompt (`NANOCODE_PROVIDER`, `NANOCODE_MODEL`, an API key from `ANTHROPIC_API_KEY` or `OPENAI_API_KEY`, else the Tempo CLI wallet, `NANOCODE_RELAY_TOKEN` to take a machine through the relay, and `NANOCODE_WORKSPACE_TOOLS` (`all`, `simulated`, `files` or `none`) to give the session a workspace in the console's data directory with those tools, and `Console hand|runner` the same selection), or `Console hand|runner <url> <token> [name]` to make the process a hand or attachment runner. `Examples/Demo` is the nanocode.xyz demo as an AppKit app for macOS and a UIKit app for iOS, in the ChatGPT or Claude style (View menu, ⌘1 and ⌘2, or Settings). Settings is a page inside the main window, not a separate window or sheet (`SettingsNode` in `Shared/Settings.swift`): the account row at the bottom of the sidebar (`CloneProps.sidebar`: the Tempo Wallet, plan or API keys with what it has spent) or ⌘, opens it over the conversation, drawn in the clone's skin as grouped tables of rows with checkmarks, native switches (`NSSwitch`, `UISwitch` tinted with the Claude accent) and inline fields, for the account (how turns are paid, the wallet with its device code, spend per service, Add MACH and Disconnect, plan sign-ins, API keys, paid tools), where the agent runs, the style, the workspace folder, the relay command and this device as a hand, with safe-area padding on iOS; `-NanocodeSettings YES` opens it at launch. The agent runs on this device, Cloudflare or Vercel (`-NanocodeRunner device|cloudflare|vercel`, ⌥⌘1 to ⌥⌘3) (`project.yml` for XcodeGen; run `xcodegen generate` there, the project is not committed): conversations from the store, a model menu, a Tempo Wallet card, device tools (`device_info`, `open_url`, `clipboard`, `speak`, and in `Shared/DeviceTools.swift` the ones behind a system permission: `photos` (list, view, save as JPEG into the workspace, read text with Vision, add to the library), `contacts` (search, list, create, export as vCard), `calendar` and `reminders` (EventKit full access), `location` (Core Location and Apple Maps search), `notify` (local notifications, and on iOS one when a turn finishes in the background), `listen` (microphone and on-device speech recognition when the device has it), `bluetooth` (a BLE scan), `compose` (a prefilled message or email the user sends), `shortcut` (runs a Shortcut through the Shortcuts app), and on iOS `camera` (a photo, or a document scan with its text), `motion` (steps and activity) and `music` (the library and the system player); each writes what it saves under the workspace, where the shell reaches it), a workspace folder the user can choose (Settings ▸ Workspace: an `NSOpenPanel` sheet on macOS, the Files app's folder picker on iOS, kept as a bookmark and opened with security-scoped access, so sessions, the shell and the hand work on the folder's real files), a computer connected through the relay, and this device as a hand. The demo sends no instructions of its own, as nanocode-ts's hosts send none: models get upstream nanocode's prompts and tool text, the session environment and the host tools' descriptions. Launch arguments script it for checks: `-NanocodeWallet cli`, `-NanocodeProvider`, `-NanocodeModel`, `-NanocodePrompt`, and `-NanocodeShell '<script>'`, which runs a script in the simulated shell in the workspace and prints its output and exit status to stdout (`simctl launch --console-pty` shows it from a simulator). The same project builds `NanocodeAppKit-macOS` (`AppKit/main.swift`, an `NSWindow` around `NanocodeChatViewController`) and `NanocodeUIKit-iOS` (`UIKit/AppDelegate.swift`, a `UINavigationController` around it with the wallet in a sheet), the smallest hosts of `NanocodeKit`'s `NanocodeChatViewController`. `project.yml` signs every app with Apple Development for the team `C3Q4NN5ZQ8` (`DEVELOPMENT_TEAM`, automatic signing; pass `-allowProvisioningUpdates`, and `DEVELOPMENT_TEAM=<team>` for another team): until 2026-10-28 it signed the Mac apps ad hoc, which changed the code signature on every build, so macOS asked for the login keychain password for every Keychain item the new build read (the wallet, plan sign-ins, API keys), while a team signature keeps one "Always Allow" across rebuilds. The demo reads only the Keychain items the current setting needs (the wallet for Tempo, the plan store for a plan, the API keys for keys, the deployment tokens off this device), and all of them when Settings opens; `CODE_SIGNING_ALLOWED=NO` checks that they compile. This Xcode had no simulator runtime on 2026-10-27; on 2026-10-28 it had iOS 18.2 and 26.5, with `simctl` and `devicectl` outside `xcrun`'s path (`/Library/Developer/PrivateFrameworks/CoreSimulator.framework/Versions/A/Resources/bin/simctl` and `CoreDevice.framework/Versions/A/Resources/bin/devicectl` beside it), so `simctl install` and `simctl launch <device> xyz.nanocode.demo` run the demo in a simulator and `devicectl device install app --device <id>` puts a signed build (`-allowProvisioningUpdates DEVELOPMENT_TEAM=<team>`) on a paired phone. `-NanocodeHand '<nc hand command>'` connects the device as a hand at launch, so a `nanocode exec --runner-host 127.0.0.1:<port> --runner-mode replace` brain on the Mac runs its tools in a simulator.
- Agents can also run on a deployment of gakonst/nanocode-ts instead of in the app: `RemoteSession` (`Sources/Nanocode/Remote.swift`, plain Swift over `URLSession`) speaks the Cloudflare adapter's protocol (`POST {base}sessions/{id}/turns?live=1&after=<seq>` with `request_id`, `prompt`, `provider`, `model`, `thinking`, `images` and `hand`, answered with Server-Sent Events of the SDK's `LoggedEvent`s until the turn's `result`; `GET …/events?live=1&after=` to reconnect and `?after=&limit=` for a JSON page; steers as a turn with `steer: true`, which a 409 refuses; `…/turns/<id>/cancel`; uploads to `…/files?name=`; and `POST …/hands` for an `nch_` hand token), which the public nanocode.xyz/cloudflare route serves with an `x-nanocode-visitor` header of 64 hex digits and the models of nanocode-cloudflare-durable's `PUBLIC_MODELS`, and the Vercel adapter's (`POST /api/chat` with `harness`, `model`, `effort` and `warm: true` for a `sessionId`, then `{sessionId, text, attachments}` answered with Server-Sent Events of mapped `LiveEvent`s whose cursors are `<drive>.<index>` and end in `;end`; `GET ?sessionId=&cursor=` to reconnect; `kind: steer` and `kind: cancel`), with `authorization: Bearer` when a token is set. Each conversation has a `RemoteConversation` record (server session, cursor, the turn in flight, the hand) in `RemoteStore`'s `conversations.json` and an append-only journal `<id>.jsonl` of what the app received (`{"logged": …}` for Cloudflare's events with a seq, `{"live": …}` for Vercel's events and the app's own prompts as `user` events, since Vercel's stream carries no prompts and each drive's cursor restarts), from which `replay()` rebuilds the transcript; `resume()` follows a turn left open from its cursor and, on Cloudflare, pages events the app missed. `Chat` attaches to any `ChatBackend` (`Session` and `RemoteSession` conform; `Chat.session` is the local one), and `Transcript` hands `apply` an event that adds no entry and is not text, reasoning, a tool event, a prompt or a turn's end (Vercel's `usage`) without ending the paragraph being written, as nanocode-ts's does since 2026-10-27, because Vercel sends a model call's usage before its last text delta and the reply split mid-sentence. ## Bridge

`nanocode_start(config, length, callback, context)` starts a runtime for a data directory (`{"data_dir", "tempo_home"?}`), `nanocode_send(handle, bytes, length)` sends one command and `nanocode_stop(handle)` closes every session and hand and shuts the runtime down; it blocks, so Swift calls it from `deinit` off the main actor. Every message either way is one JSON object. Swift sends `{"id", "command": {"<name>": {fields}}}` (externally tagged, as nanocode-ts's commands) and gets `{"reply": id, "ok"}` or `{"reply": id, "error"}`; a command without `id` gets no reply. Rust sends `{"event": {"session", ...}}` (`logged` and `live` batches of the SDK's `LoggedEvent`s, `driving`, `turn` with the finished turn's report, `waiting`, `resumed`, `error`), `{"call": {"id", "kind": "tool", "body": {name, input, context}}}`, which Swift answers with the `reply` command, `{"hand": {"id", "event" | "stopped"}}` and `{"runner": ...}` alike, `{"wallet": {"prompt"}}`, `{"payments": {"status" | "notice"}}` and `{"log"}`. The callback runs on the runtime's threads; `Router` in `Runtime.swift` resolves replies and yields events into `AsyncStream`s synchronously, so a session's events stay in log order.

Commands: `models`, `sessions` (stored root sessions, newest first), `open` (a `Configuration`, see `config.rs`, which denies unknown fields), `close`, `submit`, `steer`, `move_queued`, `replace`, `cancel`, `turn`, `pending`, `page`, `settings`, `compact`, `checkpoint`, `permission_mode`, `settle`, `interrupt_subagent`, `close_subagent`, `reply`, `mcp_sign_in`, `mcp_sign_in_wait`, `plan_sign_in`, `plan_sign_in_complete`, `plan_status`, `plan_sign_out`, `hand_start`, `hand_stop`, `hand_status`, `runner_start`, `runner_stop`, `runner_status`, `shell_run`, `wallet_connect`, `wallet_use`, `wallet_cli`, `wallet_forget`, `payments` and `funding_url`. `open` builds one `Nanocode` runtime per session (`without_runners`, the session's workspace or `<data_dir>/workspace`) and opens its `TurnInbox`; a driver task per session calls `TurnInbox::drive` whenever a submit wakes it, retries `Waiting` and `Interrupted` turns with a backoff from 0.5 s to 30 s, and reports each finished turn. An `open` with `fork` (`session`, an open session's id) starts a new session from that one's conversation through `Runtime::switch`, which forks it when the configuration keeps the model and otherwise carries its transcript to the configuration's model or provider; with `checkpoint` (from the `checkpoint` command, taken before a turn) and `before` (that turn's request id) it forks the conversation as it was before that turn. The new session gets its own ID, which the reply carries, a copy of the parent's log up to the fork point, and a place in `sessions`.

## Simulated shell

`shell.rs` runs nanocode-ts's simulated bash (`nanocode-ts/bash`, its `src/bash/`: the parser, the interpreter and its 118 commands, the shell the Cloudflare and Vercel demos give their sessions) over the device's real files, for iOS, where apps may not spawn processes. `scripts/build-shell.sh` takes `src/bash`, `src/internal` and the Code Mode cell prelude (`src/wasm/prelude.js` and `prelude/`) from `../nanocode-ts` at `origin/main` (`NANOCODE_TS` and `NANOCODE_TS_REF` override them; `NANOCODE_TS_REF=worktree` takes the checkout with its uncommitted changes through `git stash create` and records its `HEAD` with `"modified": true`) with `git archive`, bundles the shell with nanocode-ts's rolldown into the IIFE `Sources/Nanocode/Resources/shell/bash.js` (1.0 MB), copies the prelude beside it and records the revision in `ts-revision.json`. These files are generated: change the shell in nanocode-ts and rerun the script; only `Resources/shell/host.js` is written here. The shell's JavaScript is a resource of the `Nanocode` target, not part of the Rust library: `NanocodeRuntime` passes its directory as `shell` in `nanocode_start`'s configuration and the shell thread reads it when it starts, so a change to it rebuilds no Rust. `Host.shell` is one `Shell` per runtime, started by its first command, which compiles the bundle once and keeps its QuickJS bytecode in `<data_dir>/shell/bash-<sha256>.qjsbc` (73 ms to compile on an Apple silicon Mac, 4 ms to load): a thread (`nanocode-shell`, 32 MiB of stack) with an rquickjs runtime of its own (1 GiB memory limit), apart from Code Mode's, that evaluates `host.js`, the prelude (its lazy modules as JSON string literals in `lazySources`, as nanocode-ts's `cells.rs` writes them; so the shell has the cells' `TextEncoder`, `URL`, `Blob`, streams, `AbortController`, `crypto` and `fetch`) and the bundle, and calls `Bash.create` with a `FileSystem` of native calls (`stat`, `lstat`, `read`, `write`, `list`, `mkdir`, `remove`, `rename`, `chmod`, `utimes`, `symlink` and `readlink`, failing with POSIX codes such as `ENOENT` and `EACCES`). ## Machine payments

`payments.rs` is gakonst/nanocode-machines's `nanocode-mpp` layer moved into a library: `Mpp` is a `nanocode::http::Layer` that runs mpp-rs's 402 flow (`send_with_exchange` over the layer's `Next`) against `openai.mpp.tempo.xyz` and `anthropic.mpp.tempo.xyz`, preconnects each service once per wallet, keeps prepaid vouchers (`PREPAID_REQUESTS`), and attaches an `EventHook` that hands `payment-need-voucher` and `payment-receipt` SSE events to the session provider, which consumes them so neither backend's parser sees them. Channels live in `<data_dir>/payments/channels.db`, or in the Tempo CLI's shared store when the wallet is the CLI's. Spend comes from mpp-rs's `ClientEvents` and reaches Swift as `payments` messages (`PaymentStatus`). Without a wallet a paid request fails before it is sent with `tempo_wallet_required`.

A wallet is either the Tempo CLI's (`wallet_cli`, `TempoAccountsWallet::try_from_default_store`, macOS) or an access key the app's own Tempo Wallet approved: `wallet_connect` generates a secp256k1 key and runs the Accounts SDK's device-code exchange natively (`https://wallet.tempo.xyz/api/auth/device/register` with a PKCE challenge and an `rpc-requests` envelope holding `wallet_connect` with `authorizeAccessKey`, then `/token` polls), with nanocode-ts's limits (2 MACH, and 0.1 USDC.e and 0.1 pathUSD for fees, one day; pathUSD since 2026-11-08, because Tempo takes no fee in MACH, which has no FeeAMM liquidity, and an account holding pathUSD but no USDC.e could not pay the fee that lands its key) and scopes (MACH transfers and its swapper approval, the swapper, and the TIP-1034 escrow's open, top-up, close and withdraw). The prompt (`user_code`, `verification_uri`) reaches Swift as a `wallet` message; the approved record returns to Swift, which keeps it in the Keychain (`Wallet`, service `xyz.nanocode.wallet`) and installs it with `wallet_use` on later launches. mpp-rs attaches the key's authorization to its first transaction, so no separate publication is needed. The `/token` polls ride out the network (2026-11-08): approving in Tempo Wallet sends the app to the browser, iOS suspends it, and the poll in flight came back as "error sending request", which ended the connection with "polling Tempo Wallet failed" (gakonst/personal's owner could not connect from the iPhone); a poll that fails to send, or that Tempo Wallet answers with a 5xx or 429, is now tried again at the next interval until the 10-minute approval deadline, whose message names the last failure. A 200 whose body cannot be read (the same broken connection can fail after the status arrives) is polled again too, where it used to end the connection with "Tempo Wallet returned no response: null" (2026-11-09); whether Tempo Wallet answers an approved code a second time has not been tried, so that poll may still end with its refusal. A scoped key's authorization can be too heavy for an MPP service's fee payer (gas 9.6M refused as over the sponsor policy); nanocode-ts's server payer lands such a key with a self-paid transaction first (its AGENTS.md, 2026-11-08), which this crate's own payer does not do yet.

Measured on 2026-10-27 with the Tempo CLI wallet: `Examples/Console` asked Haiku 5.5 to call a Swift `clock` tool from Code Mode and answer, which cost 0.002182 MACH, and Luna 0.001169 MACH.

## Computer use

`NanocodeComputer` (macOS; its sources are `#if os(macOS)`, Swift 5 language mode; no Rust, so it builds without the FFI) is computer use over Accessibility and ScreenCaptureKit served as an MCP server on stdio, moved from tempoxyz/pyramid's `PyramidComputer` on 2026-11-05, where Pyramid.app runs it as `Pyramid --computer mcp` for the `computer` tool of its Hand (pyramid-core's kernel-computer starts it as the default macOS provider). The Rust engine `nanocode-computer` does the same natively; this one runs inside an app so macOS holds that app's Accessibility and Screen Recording grants responsible. A host calls `ComputerCommand.run(arguments, host: ComputerHost(name:command:environment:server:helperKey:))`, which never returns: `mcp` (one tool per action: `list_apps`, `get_app_state`, `click`, `drag`, `perform_secondary_action`, `press_key`, `scroll`, `select_text`, `set_value`, `type_text`), `cua-repl` (the `cua_repl` contract: `js`, `js_reset` and `turn_ended`, a persistent JavaScriptCore REPL with a `cua` API), `doctor [--prompt]`, `call <tool> [json]` and `tools`. `name` is the word tool text, the policy's refusal and the agent cursor's label use, `command` the usage line's prefix, `server` the MCP server name, the JavaScript context's name and the temporary folder of screenshots, `helperKey` the helper bundle's Info.plist key, and `environment` the prefix of every setting: `_ALLOW`, `_DENY` (bundle identifiers, comma-separated) and `_ALLOW_ALL=1` over the built-in refusals (terminals, password managers, authentication dialogs, and the host app itself), `_MAX_NODES` (accessibility elements per tree, 1500), `_SETTLE_MS` (500), `_IMAGE_FORMAT=jpeg` and `_MAX_IMAGE_BYTES` (400,000: JPEGs step down in quality until they fit, at full size so coordinates stay exact; kernel-computer passes its own screenshot limit), `_CURSOR=0`, `_INPUT=hid`, `_MOUSE` (`cg`, `cgwin`, `nsevent`, `skylight`), `_FOCUS=1` and `_HELPER`. The defaults are Pyramid's, which its Hand has run with; a host overrides them through its environment. `ComputerCommand.isHelper(host)` answers whether this process was started from the helper bundle (opened from Finder or Spotlight), which an app should then exit. The helper bundle exists because AppKit checks every process that starts an `NSApplication` in with Launch Services as the bundle its executable path is in: run from `Pyramid.app/Contents/MacOS/Pyramid`, computer use checked in as Pyramid.app itself, and once the menu bar app was gone, opening Pyramid tried to activate that UI-less process ("The application is not open anymore"). So before AppKit starts it executes itself again through a symbolic link in `<Application Support>/<app ID>/Computer/<FNV-1a of the executable path>/<name> Computer.app` (identifier `<app ID>.computer`, `LSUIElement`), built beside it and renamed in whole so a second process never runs a half-made one, keeping `argv[0]` the app's executable; the link leads to the same signed executable, so the app's grants still apply. The agent cursor is a click-through overlay panel that glides to where the agent acts and pulses on clicks, only when the target window is the frontmost at that point, labeled `name` in a pill as wide as the label plus 12 points (58 for "Pyramid", as before). `press_key` and `type_text` refuse when the app's focused window or element moved since `get_app_state`, a new `_scope` argument (a turn) starts from the full tree instead of a diff, and display screenshots leave out this process's windows and those of refused apps. Built with `swift build` and inside tempoxyz/pyramid's Mac app; not run since the move.
